# 项目级 Chat + 工作台 Agent 工作台体验设计

日期：2026-11-11
状态：已与用户确认的产品基线；本文只做设计，不代表已经实现。

## 1. 意图与问题

MAFW Desktop 应以**项目**为单位，让人和 Agent 在同一个工作空间里完成从意图到可信变更的闭环。

当前实现虽然把 Chat、Pod 和右 dock 放在同一屏，但它们主要是导航级连接，而不是稳定的工作闭环：

- Pod 呈现为平行工作空间，Lead / Tech Lead / Goal / 资源的关系不够自然；
- 从 Goal 进入 Tech Lead 或执行会话时，右侧 Goal 详情会被关闭；
- 右 dock 的「工作 / 工作台 / 执行 / 审阅」混用了工作对象、工具、运行状态和动作四个分类维度；
- 文件、文档、网页和结果产物缺少统一而自然的打开、返回、引用与修改体验；
- Goal 详情容易把内部 ID、phase、Loop、verdict、任务板和执行轨迹置于人的判断之前。

本设计重新定义产品体验，不要求保留现有四个右 dock 一级 Tab，也不要求沿用当前 Pod 页面结构。

## 2. 产品定位与北极星

> **MAFW 是以项目为单位的 Agent 工作台：Goal 定义期望，Chat 承载意图与判断，工作台呈现实际内容与变化，Tech Lead 把人的判断转化为修改，Pod 在背后提供团队执行能力。**

北极星是：

> **缩短从意图到可信变更的时间，并降低发现错误方向后纠正它的成本。**

“可信变更”意味着用户能够知道：

1. 为什么改；
2. 实际改了什么；
3. 是否符合预期；
4. 哪些评审意见已经解决；
5. 哪些剩余风险被人明确接受。

不把这些指标当作核心成功指标：消息数量、工具调用数量、表面自动化程度、Agent 角色数量或 Goal 数量。

## 3. 第一性原理模型

### 3.1 期望、实际与判断

| 概念 | 回答的问题 | 职责 |
|---|---|---|
| 项目 | 工作为什么能持续保有上下文？ | 持久的世界、资源、历史与权限边界 |
| Chat + Goal | 应该是什么？ | 讨论并稳定意图、目标、约束与验收期望 |
| 工作台 | 实际是什么？ | 呈现当前内容、进度、变更与证据 |
| Agent / Tech Lead | 如何改变实际？ | 把方向与意见转化为实际修改 |
| 人 / 审阅 | 差距是否闭合？ | 评价变化、写意见、接受或打回 |

核心回路不是一次自主执行，而是：

```text
期望 → Agent 修改实际 → 人检查实际与变更 → 人作出判断
     → Tech Lead 根据判断继续修改 → 人再次审阅
```

### 3.2 最小交互单元

```text
选择一段实际内容
→ 人写意见或直接修改
→ Tech Lead 修改并回应（意见路径）
→ 工作台呈现关联变更
→ 人确认解决或继续评审
```

### 3.3 四种一致性

- **指代一致**：Chat 中的“这段 / 这里 / 这个页面”必须对应准确的文档、代码或网页锚点。
- **时间一致**：意见、文件版本、Goal revision 和变更必须对应；旧讨论不能冒充当前版本的判断。
- **因果一致**：每条意见知道由谁回应、产生哪项修改；每次修改能追溯到意图或意见。
- **权责一致**：Agent 负责如何实现；Tech Lead 回应；Reviewer 提供证据；人确认解决、接受风险并最终验收。

### 3.4 Goal 是受管执行资源

Goal 不是 UI 任务卡，也不是项目本身。它是系统为「由 Agent 承担的意图变更」分配的受管执行上下文，具有：

- 身份与引用（Goal + revision）；
- 生命周期与可恢复状态；
- worktree、产物与评审等隔离空间；
- 执行、回应、批准、解决、验收与合并的权限边界；
- 时间、成本、轮次与并发等配额；
- 进度、阻塞、回应与结果等可订阅事件；
- 变更、证据、风险确认与提交点等审计历史。

因此：

- 项目是比 Goal 更长寿的资源命名空间；文件、讨论和 Goal 可以独立存在，Goal 引用它们而不吞并它们；
- Session 是临时连接，不是资源归属；
- run / NodeDriver 是系统利用 Goal 资源进行计算的过程，不是用户必须管理的对象；
- 直接编辑不强制 Goal；所有由 Agent 承担的修改必须持有明确的 Goal 资源；
- 需要 Goal 是系统语义，不等于用户必须先手动创建 Goal 页面。提交委托时系统可以取得或创建 Goal，归属歧义或涉及风险时必须由人选择或确认；
- 小型委托可使用轻量 Goal，避免每个小意见都获得一套重型流程。

### 3.5 注意力原则

人的注意力只应优先投向：

- 方向仍不清晰；
- 行动需要授权或涉及风险；
- 结果与变更需要评价；
- Agent 的回应仍未解决人的意见。

健康执行只提供进度，不展示执行噪声。完成告知与正式验收分离：不需要人工验收的工作也至少要让用户知道完成、结果和变更；需要验收或合并的工作仍遵守人类专属验收。

## 4. 范围、非目标与反目标

### 4.1 本轮范围

- 项目级 Chat + 内容工作台的一体体验；
- Lead → Tech Lead 的 Goal 交接与角色切换；
- 项目文件树、内容面、返回与可选并行工作 Tab；
- 按验收、阅读、修改三种意图呈现内容；
- Goal 的方向、进度、结果与变更三类用户界面；
- 可追踪的评审意见及其处理闭环；
- 人工直接编辑与 Tech Lead 修改两条路径；
- 默认隐藏的执行技术详情入口；
- 未解决意见的风险确认后强制验收；
- 项目、Goal revision、文件作用域和界面状态恢复。

评审意见持久化、风险强制验收记录等如果需要 gateway / SDK 支持，属于本轮范围；这不是纯前端换皮。

### 4.2 非目标

- 个人 Agent、跨项目长期委托和个人自动化；
- 新 Agent 角色或第二套 Goal 执行器；
- 改变 NodeDriver 的基本执行语义；
- 让 Agent 代理人类评审解决、风险接受、验收或合并；
- 让每次打开内容都创建一个持久 Tab；
- 为普通用户默认暴露完整执行轨迹、工具调用和节点日志；
- 在本设计中确定具体组件拆分、数据库 DDL、事件名或最终像素尺寸。

### 4.3 反目标

即使功能齐全，出现以下情况也算失败：

- 用户必须理解 Pod、隐藏 Session 或 runtime 角色才能推进工作；
- 切换讨论负责人会丢失当前 Goal、文件或评审状态；
- 用户读完文档后不知道如何返回原工作；
- Goal 执行过程比方向、进度和人的判断更显眼；
- Tech Lead 可以自行把人的意见标成已解决；
- Reviewer PASS 被当成人类已经验收；
- 强制验收没有明确展示剩余意见与风险。

## 5. 信息架构与布局

### 5.1 一个项目工作空间

```text
┌─────────────────────────────────────────────────────────────┐
│ 当前项目 · 当前负责人 · 注意力 / 搜索 / 团队入口              │
├──────────────────────┬──────────────────────────────────────┤
│ Chat                 │ 项目内容工作台                        │
│ Lead 或 Tech Lead    │ 上下文 / 返回 / 文件作用域             │
│ 持续讨论与判断        │ 当前 Goal / 内容 / 进度 / 结果与变更   │
│                      │                                      │
│ 输入与引用            │ 可选文件树 + 当前内容面                │
└──────────────────────┴──────────────────────────────────────┘
```

- 左侧 rail 继续承担项目导航、搜索、团队状态与全局入口；具体结构允许重组。
- Chat 与内容工作台是主组合，不能因右侧面切换而相互销毁状态。
- Pod 不再作为平行工作空间；团队状态与成员入口是项目属性。
- 现有「工作 / 工作台 / 执行 / 审阅」不再必须作为四个平级一级目的地。它们的能力按当前项目、Goal 和内容意图重新归位。
- Focus 只是临时扩大内容面，Chat、Goal 和文件状态必须保留。
- 窄窗可采用 Chat / 内容切换，但这只是空间适配，不改变二者的逻辑归属。

### 5.2 项目首页

项目首页至少直接可达：

- Lead 项目对话；
- 当前 Goal、待处理事项与结果；
- 项目文件树与最近内容。

项目首页不是执行 Dashboard，也不要求所有信息同时展开。

### 5.3 文件树、内容面与 Tab

三者职责不同：

- **文件树**回答“内容在哪里”；
- **内容面**回答“现在看什么、如何评价或修改”；
- **Tab**回答“用户正在并行保留哪些工作”。

文件树采用**状态常驻、显示随任务**：

- 项目浏览、文件阅读与修改时默认显示；
- Goal 方向讨论、纯净文档阅读、结果验收时默认收起或弱化；
- 对照代码、定位产物时按需展开或分屏；
- 展开目录、选中文件、滚动位置与草稿按项目保存；
- 用户显式显示 / 收起的偏好按项目恢复。

普通单击使用当前内容面或临时预览，不创建持久 Tab。只有以下情况进入并行工作 Tab：

- 用户显式保持打开；
- 用户要求分屏或对照；
- 用户开始一个需要持续保留的直接修改现场。

写意见给 Tech Lead 本身不要求留下文档 Tab。

## 6. 项目、Lead、Tech Lead 与 Goal 生命周期

### 6.1 项目入口

打开项目时恢复该项目的 Chat、Goal、文件树和最近内容状态。默认项目对话是 Lead。

Lead 负责项目意图、整体进展和工作分派，不处理 Goal 的技术细节。

### 6.2 取得或继续非终态 Goal

- Lead 创建 Goal 后，Chat 切换为 `Tech Lead · Goal 标题 · 当前 revision`；
- 用户也可以在阅读或讨论中先选择内容、形成意见草稿；真正提交 Agent 委托时，系统必须取得一个非终态 Goal 资源；
- 归属明确时，系统可以创建或推荐 Goal，并告知创建 / 选择依据；存在多个合理归属、可能修改错误 Goal 或涉及风险时，必须让人选择或确认；
- 自动取得 Goal 必须保留用户委托、来源讨论与资源分配记录，不能在用户不知情时启动隐藏后台工作；
- 右侧打开同一 Goal 的方向视图；
- 不关闭项目文件状态，不跳转到一个独立 Pod 工作空间；
- 继续现有非终态 Goal 时进入同一 Goal 的 Tech Lead 讨论；
- 终态 Goal 只打开历史讨论或结果快照，不重新 ensure 一个已结束讨论会话。

用户始终可以显式返回项目 Lead；返回 Lead 不应强制关闭当前内容。

### 6.3 方向与计划承诺

方向视图呈现：

- 目标与期望；
- 约束和不可牺牲项；
- 待决方案及取舍；
- 已确认决定；
- 未决问题。

需要人工批准的计划属于方向与承诺确认的一部分。计划批准继续绑定当前 plan / eval 内容；内容改变后旧批准必须失效。不要为了领域完整性默认展开全部计划执行细节。

### 6.4 执行进度

健康执行时只显示：

- 人类可读的当前阶段；
- 真实任务完成情况或可靠的定性进展；
- 最近一条有意义的进展；
- 是否需要人处理。

没有可靠百分比时不伪造百分比。当前 run、子代理、工具调用、终端日志、Loop 和节点时间线只进入显式「技术详情」。

执行中出现需要人回答的问题、方向变化或失败时，才升级为注意力事项。

### 6.5 结果与变更

结果阶段仍保留 Tech Lead 讨论。默认呈现：

1. 结果是否符合预期；
2. 本次实际修改集；
3. 可运行预览、差异、报告和测试输出等证据；
4. 评审意见及其状态；
5. 验收、打回或继续讨论。

审阅变更时使用变更集导航，而不是强迫用户先浏览整个项目文件树；需要时再定位到完整文件。

Reviewer PASS / UNREVIEWED / FAIL 是证据与评估，不是人类已经验收。

### 6.6 打回与验收

- 打回后进入新 revision，继续 Tech Lead 讨论；旧版结果、意见和证据不可改写。
- 未解决意见随新 revision 继续追踪，并保留原始锚点与历史；已解决意见留在旧版历史中。
- 验收结束后 Chat 返回项目 Lead，结果对象和历史仍可查看。
- PASS 不自动合并；验收与合并继续遵守现有人类专属权限与 worktree 合并门。

## 7. 内容打开：按意图而不是按资源类型组织

底层可以统一资源身份与打开语义，但界面不把所有资源暴露成平级对象 Tab。

### 7.1 三种意图

| 意图 | 用户问题 | 默认呈现 | 主要动作 |
|---|---|---|---|
| 验收结果 | 做成了没有，改了什么？ | 预期与实际、变更集、证据 | 审阅、写意见、验收、打回 |
| 阅读内容 | 这里面写了什么？ | 纯净正文、代码或网页 | 阅读、定位、引用、返回 |
| 修改内容 | 哪些地方要改，怎么改？ | 可选择内容、意见与直接编辑 | 选中、写意见、直接修改、看差异 |

### 7.2 入口决定默认意图

- 从 Goal「查看结果」进入：结果与变更 / 验收视图；
- 从文件树或普通 Chat 链接打开：阅读视图；
- 用户开始选择内容：出现修改动作；
- 从验收视图打开证据：暂时阅读或检查，返回后恢复原验收位置。

### 7.3 内容类型只决定合适的 Viewer

- Markdown / 文本文档：默认预览；源码 / 编辑是局部动作；
- PDF / Office：预览、页码 / 区域 / 单元格等适用锚点；
- 代码：文件树 + 代码内容，行 / 函数锚点，差异与直接编辑；
- 网页：内部浏览器、地址与历史、截图 / 区域引用；
- 终端与测试输出：作为执行证据或高级工具，不伪装成项目文件。

外部应用打开、系统浏览器打开和外部终端都是显式次操作，不是默认打开方式。

### 7.4 返回与状态

每次临时打开都应支持明确返回。返回后恢复：

- 原 Goal 与阶段；
- 原结果或阅读位置；
- 文件树展开与选中状态；
- 未提交意见、选择集和直接编辑草稿；
- 当前 Lead / Tech Lead 讨论。

### 7.5 文件作用域

项目主目录是默认文件作用域。Goal revision worktree 是显式作用域：

- 从 Goal 选择「查看本版文件 / 变更」才进入该 revision；
- 内容头部始终明确显示项目主目录或 Goal revision；
- 不得仅因 Chat 切换 Lead、Tech Lead、Builder 或 Reviewer 就暗中改变文件根；
- 产物、批注、差异与直接编辑都携带当前作用域。

### 7.6 无 Goal 的阅读、直接编辑与委托

在项目主目录或普通项目讨论中，没有当前 Goal 时：

- 阅读、引用、自由讨论和选择内容不需要 Goal；
- 人直接修改文件不需要先创建 Goal；修改显示为项目工作区中未关联 Goal 的变更，沿用现有文件保存与 diff 机制；
- 写一般讨论消息不等于创建 Goal 评审项；
- 只有用户把内容或意见交给 Tech Lead 修改、回应、解决或验收时，系统才必须取得 Goal 资源；
- 用户可以先选择和撰写意见，提交委托时再取得 Goal；选区、意见草稿和文件作用域必须保留；
- 未关联 Goal 的项目直接编辑，没有额外的 Goal 验收义务，也不进入 Goal 评审项状态机；
- 如果之后需要 Agent 介入，用户可以将当前变更交给 Lead / Goal；是否把主目录未提交变更作为 Goal 上下文必须由人明确确认，绝不静默迁入 Goal worktree。

## 8. Goal 的显示规则

### 8.1 项目中的 Goal 列表 / 卡片

优先显示：

- 用户可识别的标题；
- 当前负责人；
- 人类可读的状态与真实进度；
- 下一步动作或是否需要人处理；
- 新结果与未解决评审意见。

内部 Goal ID、phase、Loop、goalMode、原始 verdict 和 runtime Session ID 不作为主要阅读内容。

同一 Goal 的注意力呈现应避免无意义重复；完整列表用于浏览与历史，注意力区域只突出当前需要人的事项。

### 8.2 Goal 详情

按以下顺序分配注意力：

1. 要达成什么；
2. 现在需要我做什么；
3. 当前方向、进度或结果与变更；
4. 证据与评审意见；
5. 历史、revision 和技术诊断。

不使用六阶段页面 Tab 要求用户手动操作系统流程。若保留阶段指示，它只是当前位置的只读投影。

## 9. 评审意见：Goal 内的可追踪工作项

### 9.1 意见内容

评审项只用于需要 Agent 对意见承担回应、修改或解决责任的工作。提交此类意见时，系统必须取得 Goal 资源；不存在无 Goal 的评审项状态机。直接阅读、普通讨论和项目直接编辑不自动创建评审项。

每条评审意见至少关联：

- 项目、Goal、revision；
- 资源身份与内容版本 / 作用域；
- 选区、行、页码、单元格或网页区域等锚点；
- 人的意见正文；
- 作者与创建 / 更新时间；
- 状态；
- Tech Lead 回应；
- 关联变更；
- 解决 / 重开历史。

Chat 可以展示意见与讨论，但 Goal 中的评审项是处理状态的持续真相源，不能依赖滚动聊天恢复状态。

### 9.2 状态语义

```text
待处理 → Tech Lead 回应 → 已回应 → 人确认已解决
              ↑                         │
              └──── 人重新打开 / 仍需修改 ┘
```

- **待处理**：人指出差距，Agent 尚未回应；
- **已回应**：Tech Lead 给出解释或关联修改，等待人验证；
- **已解决**：人确认差距闭合；
- Tech Lead 不得自行把意见标成已解决；
- 人可以重新打开已回应或已解决意见；
- Goal 内的直接编辑产生的内容变化进入同一变更与审阅模型，但不自动替人解决意见；无 Goal 的项目直接编辑只形成项目工作区变更，直到用户明确将其交给 Lead / Goal。

### 9.3 与验收的关系

- 未解决意见必须在结果与验收界面明确呈现；
- 默认引导用户先查看和处理未解决意见；
- 允许用户在看清未解决意见后，显式确认风险并强制验收；
- 强制验收记录操作者、时间、当时未解决意见集合与风险确认；
- 强制验收不等于把意见标成已解决；
- 风险确认与验收始终是人类动作，不提供 Agent / MCP 代理路径。

## 10. 状态与现有架构约束

实现必须保留以下边界：

- 项目是桌面工作空间与 UI 状态恢复的单位；
- Goal / revision / worktree 继续是执行与产物隔离的单位；
- 评审意见与处理状态由 gateway 持久化，Chat 只是投影之一；
- 文件树、内容面、打开历史、草稿和用户布局偏好按项目恢复；
- 业务核心只经现有 RuntimeAccess / facade；客户端只消费 MAFW View DTO + Experience Action；
- 不向客户端暴露 runtime 名、内部能力位或隐藏 Session ID；
- Lead / Tech Lead / Builder / Reviewer 等内部会话仍不回流普通 rail；
- 人工验收、计划 hash 失效、Review 证据完整性、revision 不可改写和 worktree 合并门不退化；
- 优先复用现有文件预览、Monaco、批注锚点、Diff、Goal / Pod DTO 与 SSE；是否抽新组件或状态模块由实现者决定。

## 11. 验收场景

1. **Lead 交接**：从项目 Lead 创建 Goal，Chat 进入 Tech Lead，右侧出现同一 Goal 方向，项目文件状态不丢。
2. **方向讨论**：用户与 Tech Lead 讨论约束并确认方向 / 计划；不存在必须进入 Pod 的步骤。
3. **健康执行**：只看到真实进度与是否需要人；技术详情默认隐藏且可展开。
4. **纯净阅读**：从项目或 Chat 打开文档 / 网页 / 代码，直接看到内容，不新增持久对象 Tab。
5. **意见修改**：用户先选择多处内容并写意见，提交给 Tech Lead 时系统取得 Goal；每处意见有待处理状态与准确锚点，选区和草稿不丢。
6. **直接编辑**：无 Goal 时用户也可直接修改项目内容，保存后形成未关联 Goal 的项目 diff；只有明确交给 Lead / Goal 后才进入 Goal 审阅闭环。
7. **结果与变更**：结果阶段先对照预期与实际，再逐项查看变更、网页、报告和测试证据。
8. **意见闭环**：Tech Lead 回应后意见为已回应；只有人能确认解决或重开；状态跨刷新保留。
9. **风险强制验收**：有未解决意见时默认提示处理；用户可查看剩余意见、确认风险并强制验收，意见不被自动解决。
10. **打回**：打回创建新 revision，未解决意见继续追踪，旧版证据与历史不变。
11. **验收返回 Lead**：验收后 Chat 返回项目 Lead，结果与历史仍可访问；PASS 本身不触发合并。
12. **文件作用域**：项目主目录与 Goal worktree 明确区分；Chat 角色切换不暗中改变文件根。
13. **状态恢复**：切换内容、项目、Focus 或窄窗后，Chat、文件树、草稿、评审项和返回路径保持正确。
14. **完成告知**：不需要正式验收的工作完成时仍告知用户结果与变更，不制造额外验收义务。
15. **Goal 资源分配**：归属明确时系统可创建或推荐 Goal 并说明依据；归属歧义或风险操作必须由人确认，主目录未提交变更不得静默迁入 Goal worktree。

## 12. 留给实现规划的决定

实现者可以自行决定：

- SolidJS 组件与 store 的具体拆分；
- gateway / SDK 的表、DTO、路由、事件和迁移设计；
- 现有组件复用、替换或渐进迁移的路径；
- 内容返回历史的具体数据结构；
- Tab / 分屏的具体交互细节，只要符合“显式并行工作”原则；
- 视觉 token、排版与窗口尺寸，只要遵守项目 UI 约束；
- 测试拆分与分阶段交付顺序。

这些选择不得改变本文已经确认的项目边界、角色职责、Goal 三类用户呈现、评审状态权责和人类验收规则。
