# 右主 Agent 工作台与舒适对话列设计

日期：2026-11-04

## 1. 意图

MAFW Desktop 的产品定位是 **Agent 工作台**。右侧不是辅助 dock，而是持续存在的主工作现场；chatview 是指挥、协商与决策区；左侧 rail / dock 负责导航、团队与状态发现。

当前实现仍有三个根本偏差：全页 `WorkspaceHome` 会隐藏右工作台；项目 Goal 工作与当前 run 诊断混在不同入口；chat 默认 640、composer 输入仍为 14px（对话正文在新布局下已是 16px，但散落在覆盖规则里，未收敛为明确 token）。

本设计把信息架构、尺寸、窗口和字体作为一个整体修正，不改变 Goal 领域语义、gateway API、runtime 契约或谐波记忆。

## 2. 用户已确认的决定

1. 右 dock 是 Agent 主工作台，不是 chat 的附属面板。
2. 采用 A 四主面：**工作 / 工作台 / 执行 / 审阅**。
3. chat 保留 **520 / 640 / 760** 三档，默认从 640 改为 **760**，上限仍为 760，双击回 760。
4. 对话阅读正文保持 **16px**，并把该值收敛为 chat 作用域 token；composer 输入从 14px 升到 **16px**。不全局放大设置页、导航、工具元数据或所有 UI。
5. 左 dock 在默认 1600 窗口不得通过推挤把名义 760 的 chat 实际钳到约 650；日常较窄窗口使用浮层，宽屏才允许推挤。
6. 工作台默认可用、持续存在，并可进入全宽 Focus；空间不足时先收左 dock，再让 chat 降档，不自动隐藏工作台。既有手动隐藏入口与快捷键保留；手动隐藏是用户选择，Pod 注意力等工作导航会重新打开它。

## 3. 信息架构

### 3.1 右主工作台四主面

| 主面 | 内容 | 明确不放 |
|---|---|---|
| **工作** | 项目 Goal 的「需要你 / 排队 / 进行中 / 结果 / 历史」完整工作概览；进入统一 Goal 详情 | 当前 run 的 token、子代理、后台诊断 |
| **工作台** | 文件、浏览器、终端、插件 surface 与产物预览 | Goal 列表、项目成员目录 |
| **执行** | 当前 run 概览、待办、子代理、后台、轨迹；用量与上下文继续折叠在概览 | 项目级 Goal 工作概览 |
| **审阅** | per-turn / session diff、改动与审查 | 另一套 Goal 结果或批准状态 |

- 新布局缺省进入「工作」；本轮沿用现有全局 `mafw-workbench-view` 持久化，不新增 per-project 视图键。
- 新注意力到达时更新「工作」与 Pod badge，不强行打断用户正在查看的其他主面。
- 「工作」直接复用统一 `PodWorkOverview` 读模型与 `WorkOverview` 投影；计数与可见列表一致。
- 「工作」头部保留「新建 Goal」，在原主面内展开既有 `PodGoalComposer`；`openNewGoalComposer()` 改为打开该处，不再路由到全页首页。
- Goal 详情继续只有一套标题、stage、verdict、revision、结果、批准与打回语义；首轮可继续使用统一 overlay，不复制详情状态。

### 3.2 chatview 与项目入口

- 中间列承载 Lead 项目对话、自由讨论、Goal Assignment Session、Welcome 与既有 transcript；右侧工作台不再依赖 `activeTab === "chat"` 才存在。
- Config 可以覆盖内容区，但不得销毁右工作台状态；Memory / Approvals / Triage / Automation 打开时，中间列显示对应页面，右工作台仍保持可用。
- 自由讨论仍是 Session，不计入 Goal 工作。
- 对话只保留方向、问题、决定与结果对话；不把完整运行轨迹、后台列表或子代理 roster 再复制成 transcript。
- `WorkspaceHome` 不再是默认项目首页；「工作空间」rail 目的地退役，`activeTab === "goals"` 的兼容路由重定向到当前项目 Lead / 当前会话，并打开右侧「工作」主面。
- 全部工作由右侧「工作」及其完整列表承担；需要更大空间时使用工作台 Focus，而不是恢复一个独立全页工作空间。
- Lead 卡片和自由讨论长列表不再占用首页；自由讨论入口留在左侧「讨论」面与会话导航。

### 3.3 左侧 rail / dock

- rail 保留新建、讨论、搜索、Pod、便签与 Config；移除全页「工作空间」目的地。
- 审批是安全面，保留独立 rail 目的地并继续显示待审批数量 badge；Memory / Triage / Automation 由命令面板与 Config 入口承担，不再挂在 Pod 资源目录下。
- Pod dock 是团队与状态入口：注意力摘要、Lead / Tech Lead / Builder / Reviewer、少量最近消息、邮箱与共享资源。
- 点击 Pod 的注意力摘要打开右侧「工作」，不在左侧再渲染一份完整 Goal 列表。
- Pod 不再充当 Memory / Approvals / Triage / Automation 的项目工具目录。
- 右侧隐藏的 legacy `pod` 执行资源面可暂时作为高级团队 / 记忆出口保留，但不成为第五个日常主面，也不复制工作概览。

## 4. 尺寸、窗口与响应式

### 4.1 核心数值

| 项 | 值 |
|---|---:|
| 左 icon rail | 46px（不变） |
| Chat 档位 | 520 / 640 / 760px |
| Chat 默认 / 双击 | **760px** |
| Chat 绝对上限 | 760px |
| 右工作台日常建议下限 | **720px** |
| 左 dock 默认宽 | 264px（不变） |
| 左 dock push 起始窗口 | **约 1800px** |
| 设计基线窗口 | **1366×720**（chat 自动降档，工作台保 720） |
| Electron 硬下限 | **1088×720**（兼容小屏 / 缩放，不因 1366 把窗口顶出屏） |
| 主窗口默认目标 | **1720×1000**，仍按 workArea 收缩 |

实现上保持「chat 有绝对宽度预算、工作台吃剩余」的现有模型，不把比例档换回来。

建议把 `WORKBENCH_MIN_WIDTH` 从 640 调为 720；左 dock 的 pair budget 改为 **1490 = 760 chat + 730 工作台**，使默认 264 dock 的 push 点为 `46 + 264 + 1490 = 1800`。

### 4.2 必须成立的窗口例子

| 窗口 | 左 dock | Chat | 右工作台 |
|---|---|---:|---:|
| 1088（硬下限兜底） | 关闭 / 浮层 | 约 320（护栏兜底） | 约 722 |
| 1366 | 浮层 / 关闭 | 约 600（响应式降档） | 约 720 |
| 1600 | 浮层 / 关闭 | **760** | 约 794 |
| 1720 | 浮层 / 关闭 | **760** | 约 914 |
| 1800 | 可 push 264 | **760** | 约 730 |
| 1920 | 可 push 264 | **760** | 约 850 |

- 用户已存的 520 / 640 / 760 偏好保持有效；只有缺失、非法值和缺省迁移使用新默认 760。
- 手动拖窄或较小窗口允许 chat 低于 760；760 是舒适默认，不是不可变硬下限。低于 1366 时左 dock 不推挤，chat 按护栏降档，右工作台仍保住约 720px。
- 手动隐藏右工作台的入口与快捷键保留；关闭是用户选择，状态持久化，不自动触发。Pod 注意力、审批或「打开工作」等导航会重新打开它。
- **Focus 模式**：右工作台头部提供「全宽」按钮，并注册可自定义快捷键（默认 `Ctrl+Shift+M`）。进入后工作台占满 chat + 工作台区域，chat 列隐藏但保持挂载；左 rail 与左 dock 不受影响。Focus 是会话级瞬态状态，不跨重启 / 项目切换持久化；退出按钮或同一快捷键恢复进入前的 chat 档位、主面和 surface。
- 全局 Config 可覆盖内容区，但不得销毁右工作台持久化状态；项目与会话工作流不得再因路由切换把右工作台宽度变成 0。

## 5. 对话字体与阅读度量

### 5.1 范围与现状

- 新布局中的对话正文已经通过 scoped 覆盖为 **16px / 1.7**（user message 与 assistant markdown），但值散落在具体选择器中；本轮收敛为 chat 作用域 token，例如 `--mafw-chat-reading: 16px`。
- composer 输入当前为 14px，升到 **16px**，并使用 `--mafw-chat-composer: 16px`。
- token 只定义在 `.mafw-chat` 作用域；不得直接修改全局 `@mafw/ui` 的 `--font-size-base: 14px`。
- 工具元数据、状态 badge、导航、设置页、资源页保持既有字号；代码块、表格和工具卡不被迫全局放大，仍由各自排版与横向滚动规则处理。
- 行高、composer 最大高度与既有 readline / IME / 键盘行为保持可用；不得通过布局抖动表现字号切换。composer 最大高度允许随 16px 从 200px 微调到 220px，避免可见行数明显减少。

### 5.2 与 760 的关系

当前对话容器水平 padding 为 `32px + 32px`：

- 760 列的内容宽 = 696px。
- 16px 正文的阅读度量 = `696 / 16 = 43.5em`，约 43 个 CJK 字 / 行。
- 该组合比 760 + 14px 的 49.7em 更收紧，落在经典 CJK 散文舒适带附近，同时保留混合代码、表格和工具卡所需空间；因此无需为维持 48em 再把列宽加到 832。
- 这也解释了用户体感：当前正文实际已按 16px 渲染，760 列在 16px 下是舒适的阅读度量；640 列则明显更紧。

调研证据与来源状态见 `docs/research/2026-11-04-chat-detent-default-760.md`。其中开放 PR 和用户 issue 只作为需求 / 提案证据，不写成已发布事实。

## 6. 状态、数据与迁移

- 新增主面 id `work`；持久化 `mafw-workbench-view` 时接受 `work | workbench | execution | review`。
- 既有持久化值保持原义；缺失 / 非法值回 `work`。`workbench / execution / review` 的既有二级状态不重置。
- 项目工作概览使用既有 `work.overview` 与 `pod.updated` / 既有刷新机制；左侧 Pod 与右侧「工作」不得各自维护相互矛盾的 Goal 外层状态。
- 不改变 runtime / gateway 路由、Pod 文件真相源、Goal outcome、quick `UNREVIEWED`、revision、任务文件或谐波记忆写入 / 检索机制。
- 不新增跨项目 Inbox、外部触发器、per-Goal pause 或 Session archive / restore API。

## 7. 非目标

- 不重新设计主题、色板、组件库或全部 Config / Welcome 视觉。
- 不实现自由比例档、超宽 880–1200 chat 档或全局 UI 字号缩放。
- 不在本轮把每个执行叶面板都改成可拖分屏；先保留现有工作台 / 执行 / 审阅结构与插件 surface 契约。
- 不引入新的终端、浏览器、diff、审批或 Goal 后端语义。
- 不 push、deploy 或 release；这些仍需单独批准。

## 8. 验收

1. 项目默认进入 Lead / 当前会话，右主工作台存在；不再出现全页 WorkspaceHome 把右工作台隐藏的情况。
2. 右侧四主面顺序与内容归属为「工作 / 工作台 / 执行 / 审阅」，键盘与持久化可用。
3. 新布局 chat 缺省 760，双击回 760，存量 640 不被强制覆盖；1600 窗口无推挤时实际为 760。
4. 1366 / 1600 / 1720 / 1800 / 1920 宽度符合 §4.2，工作台不消失；Focus 可全宽并恢复。
5. 对话正文与 composer 为 16px，设置 / 导航 / 工具元数据未被全局放大；CJK、Latin、代码、表格、工具卡均无横向溢出回归。
6. Pod 左栏注意力能打开右侧「工作」；同一 Goal 在左栏、工作面与详情中的标题 / stage / verdict / revision 一致。
7. Desktop 全量测试、`tsgo --noEmit -p tsconfig.json`、`electron-vite build` 与真实 GUI 冒烟通过；报告新增测试数与全量通过数。
