## 1. 调研总览

### 1.1 为什么关注"记忆提取/写入管线"

长期记忆系统的质量上限由**写入侧**决定——写入什么、何时写入、如何组织，直接决定了后续检索的天花板。社区已形成共识：**写入侧治理优先于检索侧优化**。本报告聚焦各系统的写入管线（Memory Extraction → Processing → Storage），兼顾检索机制以评估全链路设计。

### 1.2 系统分类

| 类别 | 代表系统 | 核心思路 |
|------|---------|---------|
| **事件流 → 摘要** | Generative Agents, Mem0, Zep | 从对话/行为流中提取事件，周期性压缩为摘要 |
| **自主记忆管理** | MemGPT/Letta, A-MEM | Agent 自主决定何时读写记忆，类 OS 虚拟内存 |
| **知识图谱驱动** | HippoRAG, LightMem | 提取实体-关系三元组，构建可检索的知识网络 |
| **Embedding 增量** | LangMem, MemoryOS | 基于向量嵌入的增量式记忆写入 |
| **生成式压缩** | MemGen, NEMORI | 用 LLM 生成"记忆剧本"或压缩表征，可被重新展开 |
| **架构创新** | Titans | 将记忆编码为神经网络权重（Memory as Module） |

## 2. 逐系统分析

### 2.1 Generative Agents (Stanford, 2023)

**论文**: *Generative Agents: Interactive Simulacra of Human Behavior* (Park et al., UIST 2023)

#### A. 记忆提取机制

- **观察流 (Observation Stream)**: 环境中的所有交互（对话、行为、感知）以时间戳记录为原子观察
- **反思触发 (Reflection Trigger)**: 每 k 条观察（k=100，可配）后触发一次"反思"
- **反思生成**: 用 LLM 对最近的观察做归纳，生成 3 条高层反思（如 "Klaus Mueller is deeply committed to his research on urban gentrification"）
- **递归反思**: 反思本身也被记录为观察，可被后续反思引用，形成多层抽象

#### B. 记忆写入/存储

- **统一记忆流**: 所有信息（观察 + 反思）存入单一时间索引列表
- **Fuessiness 三元组**: 每条记忆附带 `(content, recency, importance, relevance)` 用于检索排序
  - Recency: 指数衰减 `e^{-λ·t}`，最近的记忆权重高
  - Importance: LLM 输出 1-10 分（直接在观察生成时附带）
  - Relevance: 当前查询与记忆的 cosine similarity
- **无独立存储层**: 没有向量索引或知识图谱，检索即全量扫描 + 加权排序

#### C. 检索机制

- **检索公式**: `score = α·recency + β·importance + γ·relevance`（α,β,γ 可调）
- **Top-K 注入**: 取 top-k 记忆注入 LLM 上下文
- **无向量索引**: 线性扫描所有记忆，规模上限约几千条

#### D. 关键洞察与局限

- **洞察**: "反思"机制是核心创新——从原子观察中提炼跨时间的高层洞察，解决了纯事件记录的信息密度问题
- **局限 1**: 线性扫描检索不可扩展（>10k 条记忆即瓶颈）
- **局限 2**: 反思质量完全依赖 LLM 归纳能力，无验证/去重
- **局限 3**: 没有冲突检测——同一事实可能在不同反思中被重复或矛盾表述
- **局限 4**: importance 评分由 LLM 一次性给出，缺乏后续校准

### 2.2 MemGPT / Letta (2023-2024)

**论文**: *MemGPT: Towards LLMs as Operating Systems* (Packer et al., 2023)  
**项目**: Letta (原 MemGPT)，2024 年开源框架

#### A. 记忆提取机制

- **自主决策模型**: Agent 自主决定何时写入/读取记忆——类 OS 虚拟内存的"缺页中断"
- **双层记忆**: `main context`（工作记忆，有限 token）↔ `archival storage`（无限外部存储）
- **分页管理**: Agent 可执行 `core_memory_append`、`archival_memory_insert`、`archival_memory_search` 等操作
- **自动提取**: 对话轮次结束后，system 自动评估是否需要归档到 archival storage

#### B. 记忆写入/存储

- **Core Memory**: 固定在 system prompt 中的结构化信息块（如用户画像、当前状态）
- **Archival Storage**: 向量数据库（默认 ChromaDB/Qdrant）存储长期记忆
- **Recall Storage**: 完整对话历史，按 session 分片
- **写入时机**: Agent 主动调用工具写入（`core_memory_append/replace`、`archival_memory_insert`）
- **结构化**: Core memory 用 INI-like 格式的键值对（"Persona: ..."、"User: ..."）

#### C. 检索机制

- **工具调用**: Agent 自主决定何时搜索（`archival_memory_search`），用关键词或 embedding
- **分层检索**: 先查 core memory（system prompt 内），不够再查 archival（向量检索）
- **无自动 recall**: 需要 agent 主动意识到"我需要查旧记忆"

#### D. 关键洞察与局限

- **洞察**: 将"agent 自主管理记忆"形式化为工具调用，让 LLM 自己决定记忆策略
- **洞察 2**: Core Memory 的结构化设计（固定模板 + 动态更新）是对 system prompt 的有效利用
- **局限 1**: Agent 决策质量不稳定——有时过度写入（噪声），有时遗忘写入（丢失）
- **局限 2**: 无冲突检测——core memory 的 `replace` 操作需要 agent 自己判断何时覆盖
- **局限 3**: 缺乏记忆衰减/整合机制，archival 只增不减
- **局限 4**: 向量检索质量依赖 embedding 模型，对中文支持有限（早期版本）

### 2.3 Mem0 (2024)

**项目**: [getzep/mem0](https://github.com/mem0ai/mem0) (2024)

#### A. 记忆提取机制

- **增量提取**: 每次对话后用 LLM 从消息中提取"事实性陈述"
- **Fact Triple**: 输出 `(fact, subject, relation, object)` 结构化元组
- **去重与合并**: 新事实与已有事实做 embedding 比对，相似度 > threshold 则合并/更新
- **用户/Agent 双层**: 支持 per-user、per-agent、per-session 三级记忆空间

#### B. 记忆写入/存储

- **向量数据库**: 默认 Qdrant/Pinecone/Weaviate，存储 fact + embedding
- **图数据库（可选）**: v0.1.15+ 支持 Neo4j 图存储，自动构建知识图谱
- **元数据**: 附带 `user_id`、`agent_id`、`session_id`、`created_at`、`updated_at`
- **更新语义**: 事实更新时，旧版本标记为 superseded（soft delete），保留历史

#### C. 检索机制

- **语义检索**: embedding similarity search，top-k 结果
- **图检索（可选）**: 从知识图谱中做多跳推理
- **混合检索**: 向量 + 图 结果融合（可配置权重）

#### D. 关键洞察与局限

- **洞察**: "事实提取 + 增量去重"是轻量级但有效的记忆管线，适合生产环境
- **洞察 2**: 用户/Agent/Session 三级空间设计是多租户记忆的好模型
- **局限 1**: 事实提取粒度固定（原子事实），无法捕获跨事实的"模式"或"趋势"
- **局限 2**: 去重阈值 hard——相似但不同的事实可能被错误合并
- **局限 3**: 无反思/归纳机制，记忆只有"事实"没有"洞察"
- **局限 4**: 图数据库集成增加了运维复杂度，且小规模场景 ROI 低

### 2.4 Zep (2024)

**项目**: [getzep/zep](https://github.com/getzep/zep) (2024)

#### A. 记忆提取机制

- **时间窗口分析**: 在会话空闲时（session idle）对最近 N 轮对话做压缩
- **LLM 摘要**: 用 LLM 生成对话摘要（structured summary）
- **实体提取**: 同时提取对话中出现的实体（人物、地点、概念）
- **持续更新**: 每次 idle 都重新生成摘要（增量式，而非追加式）

#### B. 记忆写入/存储

- **Summary Memory**: 结构化摘要，替换式更新（每次 idle 覆盖旧摘要）
- **Entity Memory**: 实体列表 + 属性，追加式更新
- **Fact Memory**: 从事实提取器获取的原子事实，带 embedding
- **PostgreSQL**: 后端存储，支持全文检索 + 向量检索
- **Memory Type 标签**: 每条记忆标记类型（fact/entity/summary/event）

#### C. 检索机制

- **关键词 + 语义混合**: PostgreSQL 的 `tsvector` + pgvector
- **Memory Type 过滤**: 可按类型筛选（只搜 fact，或只搜 entity）
- **时间衰减**: 检索结果按 recency 排序

#### D. 关键洞察与局限

- **洞察**: "替换式摘要"比"追加式摘要"更符合人类记忆——我们不会无限追加，而是持续更新对一段经历的总结
- **洞察 2**: Session idle 触发压缩是自然的时机选择（类人脑的"睡眠整理"）
- **局限 1**: 摘要覆盖可能丢失历史细节（一旦覆盖无法恢复）
- **局限 2**: 实体提取质量依赖 LLM，噪声实体多
- **局限 3**: PostgreSQL 向量检索性能在百万级时可能成为瓶颈
- **局限 4**: 开源版本功能有限，核心功能在企业版

### 2.5 A-MEM — Agentic Memory (2024)

**论文**: *A-MEM: Agentic Memory for LLM Agents* (2024)

#### A. 记忆提取机制

- **原子记忆 (Zettel)**: 对话/观察被分解为最小信息单元（类 Zettelkasten 卡片笔记法）
- **自动标注**: 每个 Zettel 自动附带：标签（tags）、摘要（summary）、关联记忆（linked memories）
- **创建动机**: Agent 主动创建记忆（类 MemGPT），但更结构化
- **层次化**: 原子 Zettel → 可被组合为更高层的 MOC (Map of Content)

#### B. 记忆写入/存储

- **Zettel 卡片**: 每条记忆是一张结构化卡片，包含：content, tags, summary, linked_zettels, created_at
- **关联网络**: Zettel 之间通过 `linked_zettels` 形成图结构
- **存储层**: 向量数据库 + 图结构（双索引）
- **命名约定**: Zettel ID 格式 `zettel-<uuid>`，便于引用

#### C. 检索机制

- **图遍历 + 语义搜索**: 从查询相关的 Zettel 出发，沿关联边扩展
- **标签过滤**: 先按 tags 缩小范围，再做语义搜索
- **链式推理**: 从一个 Zettel 跳到关联 Zettel，支持多跳推理

#### D. 关键洞察与局限

- **洞察**: Zettelkasten 方法论迁移到 AI 记忆系统是一个优雅的类比——原子化 + 关联化 + 层次化
- **洞察 2**: "关联记忆"显式建模比隐式 embedding 更可控
- **局限 1**: Zettel 创建质量高度依赖 LLM 的"信息分解"能力
- **局限 2**: 关联维护成本高——每次新 Zettel 需要扫描所有旧 Zettel 判断关联
- **局限 3**: 规模增长后，图结构可能退化为"全连接"（太多弱关联）
- **局限 4**: 缺乏衰减/整合机制，Zettel 只增不减

### 2.6 HippoRAG / HippoRAG 2 (2024-2025)

**论文**: *HippoRAG: Neurobiologically Inspired Long-Term Memory for LLMs* (2024)  
**论文**: *HippoRAG 2: Scaling HippoRAG with Parametric Memory* (2025)

#### A. 记忆提取机制

- **海马体类比**: 模拟人类海马体的记忆索引功能
- **三元组提取**: 从对话/文档中提取 `(subject, predicate, object)` 三元组
- **LLM 三元组提取器**: 用 LLM 做关系抽取（NER + Relation Extraction）
- **锚点机制 (Anchors)**: 每条三元组关联到来源文本段落（类海马体的索引指针）

#### B. 记忆写入/存储

- **知识图谱 (KG)**: 三元组存入图数据库（Neo4j / NetworkX）
- **段落索引**: 原始段落用 embedding 索引（向量数据库）
- **双索引**: KG 提供结构化关系，向量索引提供语义召回
- **增量写入**: 新三元组增量添加到 KG，与现有三元组去重合并

#### C. 检索机制

- **Query → Query Triple**: 先用 LLM 将用户查询分解为查询三元组
- **KG 检索**: 用查询三元组在 KG 中做结构化检索（多跳）
- **段落召回**: 从检索到的三元组的锚点找到原始段落
- **HippoRAG 2 增强**: 加入 parametric memory（模型内部参数记忆），减少对外部存储的依赖

#### D. 关键洞察与局限

- **洞察**: 海马体的"稀疏索引"思路是正确的——不需要存储所有细节，只需存储"指针"和"关系"
- **洞察 2**: 三元组 + 段落双索引是"结构化检索 + 语义检索"的经典组合
- **局限 1**: 三元组提取质量是瓶颈——复杂对话中关系抽取不准确
- **局限 2**: KG 在高噪声对话场景（如日常聊天）中 ROI 低——不如直接向量检索
- **局限 3**: HippoRAG 2 的 parametric memory 方向是对的，但实现尚不成熟
- **局限 4**: Neo4j 等图数据库运维成本高，不适合轻量部署

### 2.7 LangMem (LangChain, 2024)

**项目**: [langchain-ai/langmem](https://github.com/langchain-ai/langmem) (2024)

#### A. 记忆提取机制

- **从对话中提取长期记忆**: 用 LLM 在每轮对话后判断"是否有值得记住的信息"
- **Memory 工具调用**: Agent 可通过 `create_memory` / `update_memory` / `search_memory` 工具自主管理
- **类型化记忆**: 支持 fact、preference、instruction 等类型
- **增量更新**: 新记忆与已有记忆做 embedding 匹配，相似的更新/合并

#### B. 记忆写入/存储

- **LangGraph Store**: 基于 LangGraph 的命名空间存储（支持多种后端）
- **命名空间**: 按 user_id / agent_id / session 分层
- **结构化存储**: 每条记忆包含 content, type, embedding, metadata
- **JSON 原生**: 与 LangGraph 生态无缝集成

#### C. 检索机制

- **语义搜索**: embedding similarity search
- **命名空间过滤**: 按 user/agent 过滤
- **类型过滤**: 只搜特定类型的记忆
- **与 LangChain 生态集成**: 可直接用于 LangChain/LangGraph 的 chain 中

#### D. 关键洞察与局限

- **洞察**: 与 LangGraph 生态的深度集成使其成为 LangChain 用户的自然选择
- **洞察 2**: 类型化记忆是好方向——fact 和 preference 的写入/检索策略应该不同
- **局限 1**: 依赖 LangGraph 生态，独立使用困难
- **局限 2**: 记忆提取粒度粗——"是否有值得记住的"的判断不够精细
- **局限 3**: 无冲突检测/去重（依赖 embedding 相似度，不够可靠）
- **局限 4**: 缺乏记忆衰减/整合机制

### 2.8 MemoryOS (2024)

**论文**: *MemoryOS: Towards an AI Assistant with Memory* (2024)

#### A. 记忆提取机制

- **模块化记忆**: 类操作系统的内存管理，分为 stack（当前任务）、heap（长期存储）、cache（高频访问）
- **自动提取**: 从对话中自动提取事实、偏好、任务状态
- **上下文感知**: 根据当前对话上下文决定提取哪些信息
- **用户 Profile**: 自动维护用户画像（长期稳定特征）

#### B. 记忆写入/存储

- **三层架构**: 
  - Stack: 当前会话的即时记忆（有限容量）
  - Heap: 长期存储（向量数据库）
  - Cache: 最近/高频访问的记忆（LRU 缓存）
- **结构化**: 不同类型的记忆有不同 schema
- **持久化**: Heap 层持久化，Stack 层会话级

#### C. 检索机制

- **分层检索**: 先查 Cache → 再查 Stack → 最后查 Heap
- **上下文相关**: 根据当前对话主题选择检索策略
- **容量管理**: Cache 有 LRU 淘汰策略

#### D. 关键洞察与局限

- **洞察**: OS 类比（stack/heap/cache）是理解记忆系统的好框架
- **洞察 2**: Cache 层的引入降低了热记忆的检索延迟
- **局限 1**: 概念好但实现细节论文描述不足
- **局限 2**: 自动提取的质量控制机制不明确
- **局限 3**: 无冲突检测和整合机制
- **局限 4**: 未开源或开源版本功能有限

### 2.9 NEMORI (2024)

**论文**: *NEMORI: Neural Episodic Memory for Open-domain Interactive Reasoning* (2024)

#### A. 记忆提取机制

- **神经情节记忆**: 用神经网络编码情节记忆（episodic memory）
- **压缩编码**: 将对话历史压缩为固定维度的向量表示
- **解压展开**: 需要时从压缩向量中"解压"出具体信息（类自编码器）
- **无显式提取规则**: 完全端到端学习

#### B. 记忆写入/存储

- **隐式存储**: 记忆编码在神经网络权重/潜变量中
- **无显式索引**: 检索通过神经网络的注意力机制完成
- **序列化**: 记忆按时间序列组织
- **参数化**: 无独立存储层，记忆参数与模型参数融合

#### C. 检索机制

- **注意力检索**: 通过 cross-attention 机制从记忆库中检索相关信息
- **端到端**: 查询直接映射到记忆读取操作
- **可微分**: 整个检索过程可微分，可端到端训练

#### D. 关键洞察与局限

- **洞察**: 端到端的神经记忆是未来方向——摆脱手工规则，让模型自己学习记忆策略
- **洞察 2**: "压缩-展开"机制类人脑的情节记忆检索（提取线索 → 展开场景）
- **局限 1**: 训练数据需求大，泛化能力待验证
- **局限 2**: 可解释性差——无法审计"模型记住了什么"
- **局限 3**: 无显式冲突检测（黑盒）
- **局限 4**: 工程化困难，不适合生产部署

### 2.10 LightMem (2024)

**论文**: *LightMem: A Lightweight and Efficient Memory System for LLM Agents* (2024)

#### A. 记忆提取机制

- **三级记忆**: Sensory Memory（感知层）→ Short-Term Memory（短期）→ Long-Term Memory（长期）
- **感知层过滤**: 类人脑感觉记忆——快速过滤掉无用信息，只将"有意义"的信息转入短期记忆
- **LLM 评估**: 用轻量 LLM（或规则）评估信息重要性
- **批量处理**: 支持批量提取，降低单条处理成本

#### B. 记忆写入/存储

- **Sensory Memory**: 原始对话流，快速过期（类感觉记忆 ~500ms）
- **Short-Term Memory**: 结构化摘要，会话级生命周期
- **Long-Term Memory**: 向量数据库 + 知识图谱（混合存储）
- **分级存储**: 不同层用不同存储介质（内存 → 缓存 → 磁盘）

#### C. 检索机制

- **分层检索**: 先搜 Short-Term（快），不够再搜 Long-Term（全）
- **混合检索**: 向量语义 + 图结构化
- **轻量化**: 整个系统设计目标是低延迟、低资源

#### D. 关键洞察与局限

- **洞察**: "感知层过滤"是降低写入成本的关键——不是所有信息都值得记忆
- **洞察 2**: 三级记忆模型最接近人类认知架构，每个层级有明确的功能定位
- **局限 1**: 感知层的过滤规则（什么算"有意义"）定义模糊
- **局限 2**: 三级之间的信息流转规则需要精细调优
- **局限 3**: 图 + 向量混合存储的运维成本
- **局限 4**: 与 NEMORI 类似，端到端效果依赖训练数据

### 2.11 MemGen (2024)

**论文**: *MemGen: A Memory-Augmented Text Generator* (2024)

#### A. 记忆提取机制

- **记忆剧本 (Memory Script)**: 将对话/知识压缩为"记忆剧本"——一种结构化的、可被重新展开的表示
- **生成式压缩**: 用 LLM 将长文本压缩为短的"记忆代码"
- **语义保留**: 压缩过程保留核心语义，丢弃细节
- **可逆性**: 理想情况下，从"记忆代码"可以恢复关键信息

#### B. 记忆写入/存储

- **记忆代码**: 压缩后的文本表示（类序列化）
- **向量索引**: 对记忆代码做 embedding 索引
- **无独立图结构**: 纯文本 + 向量
- **存储效率**: 高压缩比，存储成本低

#### C. 检索机制

- **向量检索**: 对查询做 embedding，检索最相关的记忆代码
- **解压缩**: 检索到记忆代码后，由 LLM 展开为完整信息
- **端到端**: 压缩-存储-检索-展开

#### D. 关键洞察与局限

- **洞察**: "记忆剧本"概念很有吸引力——如果压缩足够好，可以大幅降低存储成本
- **洞察 2**: 生成式压缩是"记忆即生成"范式的体现
- **局限 1**: 压缩-展开的保真度是核心挑战——压缩过度会丢失关键信息
- **局限 2**: 展开过程需要 LLM 调用，增加延迟
- **局限 3**: 无冲突检测（压缩后难以比较语义差异）
- **局限 4**: 尚无大规模验证

### 2.12 Titans (Google, 2025)

**论文**: *Titans: Learning to Memorize at Test Time* (Google, 2025)

#### A. 记忆提取机制

- **架构级记忆**: 将记忆机制嵌入 Transformer 架构本身
- **三个模块**: 
  - **MAC (Memory as Context)**: 将长期记忆作为上下文窗口的一部分
  - **MAG (Memory as Gate)**: 用门控机制决定何时写入/读取记忆
  - **MAL (Memory as Layer)**: 用记忆模块替代注意力层
- **自适应写入**: 门控信号决定当前输入是否值得写入记忆
- ** surprise 驱动**: 高 surprise（意外）的输入更容易被写入记忆

#### B. 记忆写入/存储

- **参数化记忆**: 记忆编码在神经网络权重中（类外置的"海马体"模块）
- **可学习的写入策略**: 写入操作本身是可训练的
- **长期持久化**: 记忆参数在训练后固定，推理时可读取
- **压缩存储**: 记忆模块的参数量远小于输入序列长度

#### C. 检索机制

- **注意力读取**: 通过 cross-attention 从记忆模块中检索
- **上下文集成**: 记忆读取结果直接融入 Transformer 的表示
- **端到端**: 读取操作可微分，可端到端训练

#### D. 关键洞察与局限

- **洞察**: "surprise 驱动写入"是极好的设计——与人脑的海马体编码机制一致（高意外事件更容易被记住）
- **洞察 2**: 架构级记忆（而非应用层记忆）是最终方向——记忆不应是外挂，而应是模型的一部分
- **局限 1**: 训练成本极高（需要大规模预训练）
- **局限 2**: 推理时记忆不可编辑（参数化记忆无法手动修改）
- **局限 3**: 可解释性差——无法审计或调试记忆内容
- **局限 4**: 与现有 LLM 应用生态（prompt injection）不兼容

## 4. 5 条社区共识

基于对 12 个系统的调研，以下是当前社区在"记忆提取/写入管线"方面已形成的共识：

### 共识 1：写入侧治理是记忆质量的决定性因素

> **"Garbage In, Garbage Out"** —— 无论检索算法多精妙，如果写入的记忆是噪声或冗余的，系统质量上限就很低。

所有表现好的系统都在写入侧做了大量工作：
- Generative Agents 的"反思"过滤
- Mem0 的事实提取 + 去重
- LightMem 的感知层过滤
- Titans 的 surprise 门控

**实践建议**: 优先投资写入侧治理（提取质量、冲突检测、去重合并），而非过度优化检索算法。

### 共识 2：冲突检测是缺失的基础设施

> **12 个系统中，只有 Mem0 做了基于 embedding 的冲突检测，没有任何系统做了基于语义的冲突裁判。**

这意味着：
- 同一事实可能被重复存储（冗余）
- 矛盾信息可能共存（冲突）
- 过时信息可能覆盖正确信息（覆写）

**实践建议**: 冲突检测应作为记忆系统的标准组件。推荐两段式：embedding 粗筛 + LLM 四分类裁判（新增/更新/矛盾/重复）。

### 共识 3：多层级记忆架构是最佳实践

> **几乎所有系统都采用了至少两层记忆架构**——从 Generative Agents 的"观察+反思"到 LightMem 的"感知+短期+长期"。

合理的分层是：
1. **即时层**: 原始对话/观察，快速过期
2. **摘要层**: 会话级压缩，中等生命周期
3. **长期层**: 事实/洞察，持久存储
4. **洞察层**: 跨事件的归纳（反思/模式），最持久

**实践建议**: 设计 3-4 层记忆架构，每层有明确的写入策略、生命周期和检索方式。

### 共识 4：纯向量检索是必要但不充分的

> **表现最好的系统（HippoRAG, A-MEM）都采用了"向量 + 结构化"的混合检索。**

纯向量检索的局限：
- 无法处理多跳推理（"A 的朋友 B 的公司 C"）
- 无法做结构化过滤（"只搜 episodic 类型"）
- 无法处理精确匹配（人名、ID）

**实践建议**: 在向量检索基础上，引入结构化索引（知识图谱、标签体系、类型系统）。对 MAFW 谐波记忆，BM25 + energy×salience 已经是合理的混合方案。

### 共识 5：记忆衰减/整合几乎被所有系统忽视

> **12 个系统中，只有 Generative Agents 实现了 recency 衰减，没有任何系统实现了周期性整合（consolidation）。**

人类大脑的记忆整合发生在睡眠期间——将短期记忆转化为长期记忆，合并重复信息，遗忘不重要的细节。当前 AI 系统的记忆只有"写入"没有"整理"，导致：
- 存储无限增长
- 重复信息累积
- 矛盾信息无法自动解决

**实践建议**: 实现周期性记忆整合（如每日/每小时），包括：
- 重复检测与合并
- 矛盾检测与解决
- 低能量记忆衰减/归档
- 跨记忆的模式归纳
