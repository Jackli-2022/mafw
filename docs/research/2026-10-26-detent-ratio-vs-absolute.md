# 工作台档位：按比例还是按绝对值？跨窗口行为调研

日期：2026-10-26
背景：工作台合并 spec 原定「三档 30/40/50（占可用宽比例）+ px 墙 320/760」。用户提出疑问：档位该按比例还是绝对值，不同窗口大小下各自怎么表现。本文用业界证据 + 跨窗口量化表回答，并给出建议。

## 一、业界做法（谁用比例、谁用绝对值）

| 产品 | 对话/面板宽度 | 依据 | 性质 |
|---|---|---|---|
| **VS Code** | 主侧栏默认 **300px**，拖拽持久化 px（min 170+）；「记住每个工具窗宽度」是显式选项 | 官方文档 | **绝对值** |
| **opencode desktop** | 对话列默认 **600px**；文件树 200px；终端高 280px；宽度持久化 px | 源码 `layout.tsx`（DEFAULT_SESSION_WIDTH=600 等） | **绝对值** |
| **Zed** | Agent Panel 右 dock 默认 **640px** | 2026-09-28 美学调研 | **绝对值** |
| **Codex desktop** | 对话**内容**限宽 ~768px（`--thread-content-max-width`）；右侧 browser 面板可拖、宽度持久化 px（跨项目共享被抱怨 #20236） | issues #16669/#10516/#20236 | **绝对值（内容限宽）** |
| **JetBrains** | 每个 tool window 宽度独立记忆（px） | 官方设置说明 | **绝对值** |
| **Kimi Code desktop** | 预览默认 = 剩余宽的一半（比例默认）+ **min 320px** + 缩窗时按 max 重新钳制；拖后持久化 px；侧栏 270px | 社区逆向 spec（官方只给结构） | **比例默认 + px 持久化 + 钳制** |
| **Claude desktop** | 打开 artifact pane 时约 50/50 | 2026-10-22 调研 | 比例（近似） |
| **iPad Split View / Windows Snap** | 1/2、1/3、2/3 等固定比例档 | OS 惯例 | **比例（固定屏语境）** |

**结论先行**：桌面 IDE/Agent 产品（VS Code / opencode / Zed / Codex / JetBrains）一律用**绝对 px**（可拖 + 持久化 + 钳制）；比例档位只出现在**固定屏幕**的 OS 分屏（iPad / Windows Snap）与聊天产品的分屏默认值。我们原方案把「比例档位」搬进可缩放桌面窗口，是混用了两套语境。

## 二、跨窗口量化（可用宽 = 窗宽 − 46px 图标轨）

**方案 A（比例档位 + px 墙 320/760，当前 spec）**

| 窗口 | 30 档 | 40 档 | 50 档 | 40↔50 间距 |
|---|---|---|---|---|
| 1200 | 346 (30.0%) | 462 (40.0%) | 577 (50.0%) | 115px |
| 1440 | 418 (30.0%) | 558 (40.0%) | 697 (50.0%) | 139px |
| 1600 | 466 (30.0%) | 622 (40.0%) | 760 (48.9%) | 138px |
| 1920 | 562 (30.0%) | 750 (40.0%) | **760 (40.6%)** | **10px** |
| 2560 | **754 (30.0%)** | **760 (30.2%)** | **760 (30.2%)** | **0px ← 三档全塌缩** |

**方案 B（绝对档位 420/520/640 + 护栏：≤ min(760, 可用宽 − 520 工作台下限)）**

| 窗口 | 420 | 520 | 640 | 640 档时工作台宽 |
|---|---|---|---|---|
| 1200 | 420 (36.4%) | 520 (45.1%) | 634 (54.9%)* | 520 |
| 1440 | 420 (30.1%) | 520 (37.3%) | 640 (45.9%) | 754 |
| 1920 | 420 (22.4%) | 520 (27.7%) | 640 (34.2%) | 1234 |
| 2560 | 420 (16.7%) | 520 (20.7%) | 640 (25.5%) | 1874 |

\* 1200 窗触「工作台下限 520」护栏。

## 三、分析

1. **比例档位在宽屏塌缩**：50 档比例值撞上 760 墙后与 40 档只差 10px（1920），2560 下三档几乎完全重合（754/760/760）——档位失去意义。px 墙与比例档位本质冲突。
2. **比例档位的文本测量不稳定**：同一档位在 1200→2560 窗口间从 346px 摆到 754px（2.2 倍）。聊天可读性取决于**绝对测量**（字号×每行字数），业界用 px 锚定正是为此（Codex 内容限宽 768、opencode 600）。
3. **绝对档位在窄窗退化**：1200 窗时 640 档被「工作台下限」钳到 634，仍在可用区；更窄（<1200）本来就切 dock overlay 模式，档位不参与布局——退化路径已被现有响应式机制覆盖。
4. **比例的合理性只存在于「固定画布」**：iPad 分屏、Windows Snap 是固定屏幕上的等分语义；桌面窗口可任意缩放，等分档位的语义随窗口漂移（50% 在 1440 是「对等协作」，在 2560 是「对话仅占 30% 但已是 760px 画幅上限」），标签会撒谎。
5. **Kimi 的混合做法可借鉴但不必照搬**：比例默认 + px 持久化 + 缩窗钳制 = 默认值按比例算一次，之后一切按 px。我们的「档位」是显式离散语义，更适合直接锚定 px。

## 四、建议（供拍板）

**改为绝对 px 档位：420 / 520 / 640**（紧凑 / 标准 / 宽阔），护栏：
- `chat = clamp(stopPx, 320, min(760, available − 520))`（工作台下限 520px：树 180 + 编辑区 340）
- 窗口 < 1200：沿用 dock overlay 机制，档位不参与布局
- 持久化：存档位 px 值（"420"|"520"|"640"）；旧 `mafw-chat-width` 迁移用「像素最近档」
- 拖动预览显示**实时 px + 当前实际比例**（比例是结果，不是档位定义）；档位标签改为「紧凑 / 标准 / 宽阔」，不再写 30·70 这类会随窗口漂移的比例标签
- 视觉伴侣里的 `30/40/50` 三档语义作废（用户原始选择是「三档」这个数量，不是比例数值）

**与业界对齐**：420（聊天舒适下限，> 现 340 旧默认）／520（≈ 现 760 墙前的常规值，opencode 600 的保守侧）／640（Zed 640 同值）。三档间距 100/120px，拖拽手感与 30/40/50 比例档在 1440 窗下几乎同构（420/520/640 vs 418/558/697）。

## 五、四家逐项（按用户追问补全）

| 产品 | 宽度机制 | 公开数值 | 跨窗行为 | 证据 |
|---|---|---|---|---|
| **opencode desktop** | **绝对 px + 持久化**（`layout.v6`） | 对话列 **600**（DEFAULT_SESSION_WIDTH）/ 文件树 200 / 终端高 280 / 左栏 344 | 对话固定 600：1200 窗占 50% → 1440 约 43% → 1920 约 31% → 2560 约 23%。**clamp 极值出过 bug**：review 面板无法缩到窗宽 ~55% 以下（对话列 max-width 帽，issue #30618）；窄窗拖拽把手失效、chat 被压到最小（#30560） | 源码 `packages/app/src/context/layout.tsx`；issues #30618 / #30560 |
| **Codex desktop** | **内容限宽绝对 + 面板绝对 px 持久化** | 对话内容 `--thread-content-max-width` ≈ **768**；右侧 browser 面板可拖、宽度**跨项目全局共享**（issue #20236） | 对话内容固定 768 居中，窗口再宽只增两侧留白（用户长期抱怨，#16669/#10516，社区靠改 CSS 变量绕过）；面板宽度不按项目记忆；多 pane 平铺仍是 feature request（#33301）；TUI 另案提案 50/50 分屏（#38073，≥120 列） | issues #16669 / #10516 / #20236 / #33301 / #38073 |
| **Claude desktop** | **自由 pane**：拖 pane 边改宽、可 pop out；**未公布默认宽度/比例** | 无公开数字 | 跨窗行为官方未文档化，不能断言。另：claude.ai 的 Artifact 分屏约 50/50 属 Web 聊天产品面，不等于 Claude Code Desktop 的 pane 默认值 | code.claude.com/docs/en/desktop（只描述交互） |
| **dsh**（DeepSeek Harness） | **dockkit 停靠面**：每会话一个 right sidebar，pane 可 split / float / collapse；**布局仅内存**（不持久化），无公开宽度数值 | 无 | 跨窗行为未定义（无数字可依）；dsh-tauri v0.25.0 给右栏加了「在新窗口全屏打开」 | 2026-09-29 面板调研；dsh-tauri v0.25.0 release notes |

**四家的共同点与教训**：
1. **没有一家在可缩放的桌面窗口上做「比例档位」**——比例只出现在固定画布（iPad/Windows Snap）和 Web 聊天分屏默认值。
2. opencode 与 Codex 都选了**绝对锚定 + clamp**，且都在**极值/窄窗**处出过真实 bug（opencode 的 max-width 帽把 review 顶到 55%+；Codex 的宽度全局共享被抱怨）。
3. Claude/dsh 干脆**不给档位**（自由拖/仅内存）——把复杂度留给用户，也躲开了档位语义。
4. 对我们：绝对 px 档位的方向与业界一致，但必须把 **min/max 钳制语义**当成一等公民测试（这正是计划 Review Focus #1/#3 覆盖的）；档位标签用绝对语义（紧凑/标准/宽阔），比例只作实时显示。
